嗨嗨！最近看大家都在做各种各样的应用，我也想把自己踩过的一些坑和零碎想法梳理一下，写出来看有没有感兴趣的同学多交流，也一起纠正一下我之前的认知偏差 www。

首先说背景，为什么有这些工程，在我的经验里，AI 的结果往往是“概率性”的，本身我们期待，temperature 越接近 0，模型的表现应该更有确定性，但是在使用一系列 llm 模型进行相同输入的时候，结果仍然存在大量的差异，为了减少这种不完全可复现对于实际生产中的影响，我们设计了很多工程性的方法去打补丁，从 prompt、agentic、Harness 和 mcp、skill 等等内容，都是为了让模型按照我们的预期去产出结果。

在做这些工具的时候，又可以把工作分成两类：一类是“模型现在不够才需要的补丁”，另一类是“不管模型多强都绕不开的设计”。很多时候会有人说面向六个月后设计，但是我们做判断的时候，本身也是受到自己的上下文影响的，之前的经验、当下的模型限制、工具失败的经验以及我们在这种不断尝试中积累下来的经验，这些内容整合在一起，共同影响我们对于六个月后工作的判断，所以了解的越多越准确，判断可能会更准确一点。

比如结构化输出，之前还花过不少精力做 JSON 校验，写格式规定、模板、兜底逻辑。后来模型原生能力增强，structured outputs 变成标配，格式错误率大大降低。但格式对了，内容可能是错的。所以对抗格式错误变成了对抗语义错误，又开始额外写一层内容校验。

然后有一些模型本身的问题，我个人认为是很难在短期有突破性进展的，所以从我的角度触发，了解这些问题和原理，可能在设计 agent 的时候有一些帮助，就算后面有了一些进展，也能很快地理解进展的突破在什么地方，它的工作是如何做的。

## 上下文问题

上下文在执行任务的时候会不断变大，而变大的上下文会反过来影响模型本身的能力，为了减少这个问题的影响，大家尝试过很多方向。

比如说增加上下文，将所有信息直接塞进去，让模型自己去用注意力权重找到它需要的信息，或许可以增强模型的回答质量。然后窗口大小就一路飙升，200k、500k、1m、无限上下文等等，但最终的结果是，上下文变成了 1m，使用体验上并没有比 200k 强五倍，反而因为上下文腐烂等问题，导致很多人觉得 1m 变得又贵质量又差。

所以一味地投入上下文增长肯定是不行的，模型侧的优化去解决 lost in the middle 看起来也很难大幅提升当下的表现效果。

然后现在很多团队就会用更加工程化的手段，去更高效地管理上下文，来提升信噪比，减少其他信息对于模型的上下文污染。

比如某知名顶级大模型团队在最近开源的代码里，就把上下文折叠做成了四级压缩管道：一级一级丢弃不需要的内容，压缩历史记忆，越轻的手段越优先用，越重的越后用。虽然压缩机制在各种项目里都能看到影子，但这种分层优先级的思路仍然有参考价值 www。

不过窗口管理只是一半，还有一个要命的问题是，喂进上下文的信息本身质量有问题。

大模型的上下文和传统状态管理不太一样。传统系统里，数据在数据库里，查什么就得到什么；但是 agent 没有一个“精确查询”的机制来保证拿到的一定是它需要的。向量检索里的“距离最近”不总等于“真正相关”，比如在传统 RAG 增强里，让 AI 去查汉堡，可能是“汉堡 → 麦当劳 → 麦当劳创始人生平”，这种无用的信息就污染了模型的上下文，后面大家又在检索上加节点关系、加结构设计、加各种复杂机制，不过做到什么程度，还是要结合具体业务需求来判断。

举个🌰，很多时候我会直接给 AI 一个参考示例让它对着抄来写代码。但那个示例代码质量就不高（可能是因为我自己写的），也没有对应模块的规范引导。结果就是 AI 学会了不规范的写法，在我的屎山上产出了屎山 plus。触发记忆机制后，它把“如何产出屎山”的经验存进 memory，后续复用时继续固化这种偏差。学得越多写得越💩。

需要注意的是，这些输出常常“看起来没有违和感”：结构清晰、命名规范、注释齐全。大模型一次性吐出千百行代码，人工 review 也很难在表层快速发现问题。而且现在的 Automation Bias 也越来越明显，看 anthropic 的 blog，也是说现在人 AI 用得越多，越倾向默认同意 AI 的请求，完全不看过程中产出的代码。

这种趋势有点不太好回避，但为了让 AI 最终交付的内容更可靠，我们也有其他很多方法，比如代码规范可以梳理出来，在初始化环节喂给 AI，校验环节可以后置，让 AI 知道产物是不是正确的，各个环节都有优化的地方。

## 拆分任务管理上下文

上下文在长任务中难以被一个模型管理，一个自然的想法是拆分。

把大型任务分配给多个子 Agent，让每个 Agent 只关注自己那部分任务。有的模式是一个 Agent 做完交给下一个 Agent，有的是 Agent 们一起边做边讨论，有的是立一个公告板让子 Agent 自己领任务去完成。workflow、Orchestrator-Workers、各种设计模式能参考的还是挺多的。

不过这些设计目的只有一个：让每个子 Agent 只关注它需要的信息。

但问题也跟着来了，它需要的信息具体是哪部分？喂多了是噪音，喂少了又缺关键上下文。

说到底，几乎所有工作都在对抗同一个问题：模型的注意力是有限的。大家试图让模型看到“刚好够用”的信息，让信噪比更高，所以出现了各种 memory 的提示、唤醒、清理、分层、结构化、时间化、更新等等机制，各种 idea 和拼接组合层出不穷。

然后拆分成子 Agent 后也有一些问题需要关注，比如错误隔离。

链路短的时候这不明显。但任务一长，如果一个子 agent 的误判混进共享状态，后面依赖这个状态的 agent 都会跟着跑偏。级联错误比上下文不足的破坏力大得多。

也就是说除了纠结“每个子任务需要什么上下文”，可能也需要去纠结一下“子任务的错误怎么隔开”。

有些框架因此做了进程级隔离：每个子 agent 有独立的上下文窗口和消息历史，agent 之间只通过结构化消息通信，不共享原始上下文（有的也共享）。还有一种协调者模式，负责分配任务的那个 agent 不拥有文件读写或命令执行的能力，它只能分配和检查结果，不能自己动手，决策层和执行层物理分开。又或者再加一个没参与过前置过程的审查节点再来 review 一下等等。

最简单的办法，在每次收到反馈的时候让模型自己 rethink 一下，看看能不能找出问题。这个可以泛化到每次 tool 调用完拿到结果的时候都反思一下。

## 写了步骤，但是模型也不听

除了上下文和拆分，还有一个高频的问题：为什么我们告诉 AI 按步骤做，它还是没有按规定去执行？

之前做的一个编辑器页面的工具，在 skill 里简单规定下了流程：1. 生成模板文件 2. 导入项目 3. 生成绑定代码。但 AI 执行时，会在生成完模板文件后直接跳到绑定代码，跳过导入步骤，导致后续工具调用失败。

除开本身的概率性以外，还有一个点：模型在每一步都会选择局部上最省事的动作，而不是基于全局依赖图推导出一个完整的执行顺序。因为模型在训练的时候大家就会为了避免模型陷入思考的循环，去奖励它打断自己，所以它在实际使用的时候，也会在认为自己了解了足够多的信息的时候，选择自己认为的最优解，直接跳过某些我们和它说的步骤。

不过我这个情况的处理方式很简单，在错误反馈里用自然语言让它重新检查前置条件就好了，在 sota 模型表现效果也能满足当下需求。但链路更长的时候，也有一些更工程化的手段，比如状态环境跟踪，在生成绑定代码的工具调用处先检查某个状态，文件没导入就触发 `XXX_NOT_REGISTERED` 的错误，然后直接执行导入并把错误反馈返回给模型。很多框架里的 checkpoint 设计也是这个思路，Plan-and-Solve，把“前置条件”的逻辑显式化，在长期执行任务里还是很有效的。

但是很多复杂的设计感觉在日常做的时候没有必要直接上，知道在什么地方可以插入，就可以先从简单框架开始，遇到问题再去解决对应的问题，根据自己的经验去判断，能减少迭代成本 www。当然强依赖顺序的环节的校验状态还是要提前设计好的。

这里提到了 skill，就再补充一下为什么现在不太建议大家开很多 MCP，或者装特别多 skill。

最大原因还是工具越多越容易出现重复或重叠语义，让模型不知道该选哪个；而且站在模型视角，很多工具本身的用途描述往往就不够清晰，也不够明确“什么时候该调用、调用后会得到什么”。所以在设计的时候，可以合并一些工具，只开启需要的功能等等，来减少模型选择的困难程度。

## 验证和评估

到我个人觉得落地中最重要的环节了 www。

前面说的各种问题，都可以设计出对应的反馈系统，及时给模型错误报告，或者触发回滚等等机制，让模型动态地去调整方向，不要错得太离谱。

这里要注意的就是不要相信一句让模型自己 review 就能检查出问题。模型的内部反馈往往会沿用模型固有的知识与参数进行评估。在缺少外部独立证据或外部工具约束时，模型可能无法真正改变关键假设，反而会在同一类错误里打转。相比之下，让其他模型或外部工具注入明确证据，更容易让它找到问题。

因此很多工具和框架会构造一个完整的循环：让模型认识到当前错误、拿到明确报错信息，然后再根据反馈纠正。

参考一些厂商的设计，它们的主循环里真正调用模型的步骤可能只有一个，但围绕这一步的校验、压缩、恢复、权限检查加起来有十几步。不是在循环外面加一道检查就行了，整个循环的骨架本身就是在做检查，调模型反而只是其中一个环节。循环里记录一个字段标明“这次迭代是因为什么才继续的”——输出被截断需要恢复，还是上下文炸了需要压缩重试，还是正常下一轮。测试可以直接断言恢复路径被触发了，不需要去解析消息内容才能判断。把“为什么继续”变成可观测的数据，比从日志里猜原因靠谱得多。

还有一个点，怎么去验证最后设计出来的工具的好坏。

在一个循环能够搭建起来、相关设施建设到最后的时候，就可以采集些真实的交互数据，设计评测任务，完整地量化每个模型在各个环节的表现了，不过这部分可能更偏向优化……有点写不动了，下次再说。

## 焦虑

上面说了很多零碎经验，但这些未必等价于模型公司正在全力投入解决的方向，不同团队里每个人关注的重点也不一样，算力更多的地方内部也会分化很多条路线一起去尝试和探究各种可能性。所以通用能力里哪些会被厂商吸收、哪些会留在工程系统里，很难有一个准确结论。

像上下文管理应该设计到什么程度？KV cache 优化在很多 Harness 框架里用得不够好，反过来影响模型表现，要不要放弃掉本地的一些设计？我们包装的能力是否反而减少了模型自身的判断力？厂商吞吃掉 Agent 设计后会不会出现标准化设计，只能做对于每个厂商都适配的工程？自进化、记忆、多智能体、垂类场景这些最后到底是什么方法最好等等，谁说得准呢（。

不过在行业落地里，围绕日常开发工作流去做必要的建设，让 AI 更了解项目状态、获得更准确的信息、更高效地利用上下文、更可靠地做长期规划与执行。在当下和未来一段时间里，都能很明显地看到效果 www。

> 很多问题在当前领域里都有大量工作在推进，但哪些真正有效、哪些更有价值，仍需要在实践中对抗噪声、不断验证。所以这份碎碎念不会把观点收敛成结论；后面有需要我会再针对具体领域比如记忆、自进化、情感陪伴等等做更细的梳理。有问题或表述不准的地方，欢迎随时 call 我。
